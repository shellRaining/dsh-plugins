# 质量与验证

## 测试权限

agent 不得自行新增或改写测试。此限制同样适用于主 agent、子 agent、临时测试脚本、测试夹具、快照和为了验证当前实现而临时拼出的断言代码。不得以委派、换文件名或在命令行内嵌测试的方式绕过。

允许运行类型检查、构建、已有静态检查和手动页面验证。需要新增测试或修改已有用例时，先向用户说明要保护的行为、当前缺口和变更范围，取得明确授权后再动手。任务要求实现功能或修复问题，本身不等于授权修改测试。

仓库当前不保留测试套件，没有可删除或弱化的断言；需要质量保障时按“实际页面验证”一节手动验证。

## 验证顺序

单包开发先运行该包的类型检查和构建。交付前在根目录依次执行：

```sh
pnpm typecheck
pnpm build
```

`pnpm typecheck` 先检查共享工具和各包构建脚本，再检查各包的类型，`pnpm build` 生成实际入口和客户端 bundle。仓库当前不含自动化测试套件，也没有 `pnpm test` 命令。

当前仓库没有统一 lint / format 命令，不要在交付说明里声称通过了未配置的检查。构建成功只说明静态产物可生成，类型检查和构建都不等于浏览器交互已验证。

收尾用 `git diff --check` 检查空白错误，审查源码、manifest、lockfile 和生成产物是否对应。交付说明列出运行过的命令、结果以及未验证的范围；检查失败不能写成全部完成。

## 实际页面验证

涉及客户端加载、宿主接口、样式或交互时，优先复用用户已经运行的 DSH Web GUI，确认插件确实从本次构建目录加载。不能拿新开的独立 Vite 页面代替 DSH 注入环境。

只在同一宿主 checkout 的 `pnpm run dev:web` 正在重建客户端 bundle 时，才可以依赖 client-plugin HMR 接收更新；否则先完成相应构建再刷新现有页面。不要未经确认承诺热更新，不要擅自改用户 profile 或另起替代服务。

按改动验证插件启停、主要交互、会话切换和清理行为；涉及视觉时检查明暗主题，涉及本地化时检查中英文。优先手动验证，不因缺少自动化覆盖自行编写测试。

没有页面控制能力、加载权限或合适环境时，明确写出未完成运行时验证，不把类型检查、构建或结构测试当成页面验证的替代。

## 发布

npm 包由 GitHub Actions 的 [release 流水线](../.github/workflows/release.yml)发布，除新包的首个版本外，不在本机执行发布。含 `catalog:` 的源码目录必须用 `pnpm publish`，或用 `pnpm pack` 后发布生成的 tarball，不能直接用 `npm publish` 跳过 catalog 转换。推送到 main 后，流水线依次安装依赖、类型检查、构建，确认提交进仓库的构建产物与重新构建的结果一致，再运行 `pnpm -r publish`。版本号已在 npm 上的包会跳过，其余包作为 latest 发布。

发版就是修改对应包 `package.json` 的 `version`，和代码一起推送到 main。没改版本号的包不会重新发布。npm 不允许重复发布同一版本，流水线在构建或检查阶段失败时可以修复后再推送；如果 npm 已经接受了某个版本，后续修复要换新版本号。

认证使用 npm trusted publishing（OIDC），仓库里不保存 npm token，发布的包自动附带 provenance。每个包在 npm 上有一条绑定本仓库 `release.yml` 的信任配置。新增插件包时，先手动发布首个版本（包在 npm 上存在后才能配置信任），再用 npm 11.15 以上版本运行下面的命令绑定，并在 48 小时内完成一次流水线发布，否则这条配置会过期失效。重命名工作流文件或迁移仓库后也要重新绑定。

```sh
npm trust github <包名> --repo shellRaining/dsh-plugins --file release.yml --allow-publish
```

npm 会在发布后扫描恶意代码，新版本通常要等几分钟才能安装。
